# DODOデータ設計（下書き）

この資料は、Aily由来のサロンデータ構造を再利用せず、DODO専用のデータを新しく分離するための下書きです。`DODO_DATA_MODEL_DRAFT.sql` はmigrationではなく、末尾も `rollback` にしてあります。ローカル・本番を含め、データベースには未適用です。

## 対象データ

- ガイド基本情報
- ガイド本人の携帯番号認証と限定セッション
- 月次Excel取込バッチと取込明細
- ガイド別月次精算とその根拠明細
- 支払バッチと支払結果
- 精算書・支払証明書・領収書などの文書管理
- 稼働報告書と署名記録

## 安全設計

- すべてDODO専用の `dodo_` 接頭辞を使い、Ailyの既存テーブルを参照しません。
- `public` に置く全テーブルでRLSを有効にし、`anon` と `authenticated` には権限を付けません。
- 現在のDODOはSupabase Authではなく署名付きスタッフCookieを使うため、将来のDB操作はサーバー側だけに限定します。
- ガイド本人用の携帯認証はスタッフCookieと別セッションにし、認証コードは平文保存せず、期限・試行回数・失効をサーバー側で管理します。
- 秘密鍵またはservice role相当のキーはブラウザーへ渡しません。
- 元ファイルと明細にSHA-256を持たせ、同一ファイル・同一明細の二重取込を防ぐ前提です。
- 円金額は小数を使わず整数で保持します。
- COM、DODO手数料、ガイド支払額の計算式は未確定のため、勝手な数式をDB制約にしていません。
- 月会費は目的・金額・対象者・徴収方法が未確定です。現時点ではDODO手数料と同じ項目にせず、取込・自動計算・差引の対象にしていません。

## 実適用前に必要な確認

1. DODOが使うSupabaseプロジェクトを特定し、Ailyと分離されていることを確認する。
2. 対象プロジェクトのバックアップと、既存テーブル・Storage bucketの一覧を取得する。
3. Ailyデータの削除対象を一覧化し、削除前にマデオ本人が承認する。
4. Supabase CLIで `supabase migration new dodo_core_schema` を実行し、この下書きを正式migrationへ移す。
5. 使い捨てのローカルDBでmigration、RLS、重複防止、ロールバック手順をテストする。
6. Preview環境で実データを使わずに取込・精算・文書生成の一連の流れを確認する。

## ローカル取込前チェック

`lib/dodo/importValidation.ts` は、DBへ保存する前に次を確認します。

- 取込元と対象月が入力されていること
- 対象月が `YYYY-MM`、稼働日が実在する `YYYY-MM-DD` であること
- 行番号が1以上の整数であること
- 金額が0以上の整数（円）であること
- 外部参照番号または明細内容が同じ行を重複として検出すること

計算式は確定していないため、各金額の相互関係はまだ判定しません。

## 精算書・受取書のローカル確定前チェック

`lib/server/guideFinancialDocuments.ts` は、DBやStorageへ接続せずに書類描画へ渡す固定スナップショットを作ります。

- 精算書は`confirmed`・`payable`・`paid`の精算だけを受け付けます。
- COM、DODO手数料、ガイド支払額は明細合計と一致することを個別に確認します。未確定の相互計算式は適用しません。
- 受取書は支払状態が`paid`で、支払額が精算のガイド支払額と一致する場合だけ作れます。
- 精算スナップショットをSHA-256で結び、後から金額や対象月を変えたデータで受取書を作れないようにします。
- 再発行は版番号2以上と差替え元の書類IDを必須にし、初版と訂正版の関係を残します。

PDFの見た目、押印・電子署名、実DB保存、非公開Storageへの保存はまだ実装していません。
