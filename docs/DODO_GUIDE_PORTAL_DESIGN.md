# DODO ガイド専用ページ設計（実装前の安全基準）

ガイド本人が携帯電話で、確定済みの精算書・支払証明書・受領証・業務完了報告書を確認するための設計です。電話番号認証・WeChat連携・データベース・Storageにはまだ適用していません。

## 利用者の流れ

1. スタッフがガイド管理で、本人確認済みの携帯番号を登録する。
2. ガイドがガイド専用ページで電話番号を入力する。
3. サーバーが6桁のワンタイムコードを送信する。
4. ガイドが10分以内にコードを入力し、本人専用セッションを取得する。
5. サーバーはセッションのガイドIDと書類のガイドIDを完全一致で照合する。
6. 確定済みの本人書類だけを、短時間で失効するダウンロードURLとして表示する。

## 必須の安全条件

- 認証コードの平文、携帯番号の生値、WeChatアクセストークンをブラウザーへ渡さない。
- 認証コードはサーバー側でハッシュ化し、10分で失効、5回失敗で再発行を停止する。
- ガイド用セッションはスタッフ用Cookieと別のCookie名・別署名鍵にする。スタッフ権限へ昇格できない構造にする。
- ガイド用Cookie名は `dodo_guide_session`、署名鍵は `GUIDE_SESSION_SECRET` とし、スタッフ用の `staff_session` / `STAFF_SESSION_SECRET` へフォールバックしない。
- 携帯認証コードは10分で失効し、5回誤入力でロックし、成功後は再利用不可とする。状態遷移は `lib/dodo/guidePhoneChallenge.ts` に集約し、生の認証コードは保存しない。
- 保存する認証コード値は、ガイドセッション鍵とは別の `GUIDE_PHONE_CODE_SECRET` を使い、チャレンジUUIDとコードをHMAC-SHA-256で結び付けたダイジェストだけとする。照合はWeb Cryptoの検証処理を使い、別チャレンジへの転用と文字列の早期終了比較を避ける。
- コード照合と試行状態の更新は `lib/server/guidePhoneVerification.ts` を唯一の入口とし、不一致だけを失敗回数へ加算する。秘密鍵などサーバー設定の不備は例外として扱い、ガイドの試行回数を消費しない。返却状態は本番導入時にDB上で原子的に保存する。
- 認証完了は `lib/server/guidePhoneAuthentication.ts` に集約し、コード照合がチャレンジを使用済みへ遷移させた場合だけガイド専用セッションを署名する。不一致・期限切れ・ロック済み・使用済みではセッションを作らない。本番では使用済み状態の原子的保存に成功した後だけCookieを返し、同時実行による二重ログインを防ぐ。
- ライブ経路は同ファイルの `completePersistedGuidePhoneAuthentication` だけを使い、チャレンジの旧状態と次状態を比較するDB側compare-and-setを注入する。更新競合時は`state_conflict`としてセッションを作らず、成功時だけ`HttpOnly`・`Secure`・`SameSite=Lax`のガイド専用Cookie設定を受け取る。この関数自身はDB・Cookie・外部通信を操作しない。
- 将来のコード確認APIは `lib/server/guidePhoneVerificationHttp.ts` の入力境界を通す。JSONはチャレンジUUIDとASCII 6桁コードだけを許可し、余分な項目・全角数字・空白・長さ違反をDB照会前に拒否する。存在しない・不一致・期限切れ・ロック・使用済み・更新競合はすべて同じ`verification_failed`応答にまとめ、内部状態を推測させない。成功時のCookie情報は原子的認証完了処理からだけ受け取る。
- 認証コードは `lib/server/guidePhoneChallengeCreation.ts` で暗号学的乱数から偏りなく6桁へ変換する。SMS事業者へ一時的に渡す平文コードと、DBへ保存できるチャレンジUUID・ダイジェスト・試行状態を別オブジェクトで返し、平文コードは保存しない。
- 発行前に `lib/server/guidePhoneIssuancePolicy.ts` で日本の携帯番号を正規化し、同一番号の再送は60秒待機、直近1時間は最大5回までとする。この判定はローカル実装だけで、実運用時は同一番号の発行履歴を信頼できるサーバー側ストアから取得し、許可した発行をSMS送信前に原子的に記録する。
- `lib/server/guidePhoneIssuancePreparation.ts` を発行準備の唯一の入口とし、発行制限で拒否した場合はUUID・乱数コード・ダイジェストを生成しない。許可時だけ正規化番号と送信用／保存用を分離したチャレンジを返すが、この段階ではDB保存もSMS送信も行わない。
- `lib/server/guidePhoneIssuance.ts` は、信頼できるガイド候補・発行履歴の取得、発行準備、チャレンジの原子的保存、SMS送信の順序を固定する。保存が競合・失敗したコードは送信せず、保存成功後の送信失敗は履歴を取り消さない。成功応答にはチャレンジUUIDと有効期限だけを含め、電話番号・平文コード・ダイジェスト・ガイドIDは含めない。この段階の保存・送信は注入した偽実装でだけ検証し、実DB・実SMSへは接続しない。
- 将来のコード発行APIは `lib/server/guidePhoneIssuanceHttp.ts` の入力境界を通す。JSONは32文字以内のASCII電話番号文字列1項目だけを許可し、余分な項目・全角数字・制御文字・過長入力を発行処理前に拒否する。形式が正しい要求には、発行成功・拒否・送信障害を問わずHTTP 202と同じヘッダー、`ok: true`・UUID v4を返す。`ok`は要求受付だけを意味し、登録済み・配信成功を保証しない。拒否・障害時のUUIDは保存も送信もしないため認証に使えない。内部障害は秘密情報を含まない固定イベントだけを非公開監視へ渡す。実HTTPルートはまだ追加しない。
- 認証準備前に `lib/server/guidePhoneGuideMatch.ts` で、正規化番号が在籍中のDODOガイド1名だけに一致することを確認する。該当なし・退職済み・重複登録は同じ内部拒否結果にまとめ、HTTP境界で上記の受付応答に変換する。許可時はガイドIDと正規化番号を保存用チャレンジへ結び付ける。応答時間からの推測への対策は別途必要とする。
- 書類アクセスはURLの推測では認めず、セッションのガイドID・書類のガイドID・書類状態`final`を毎回照合する。
- `draft`・`void`書類、他人の書類、失効したセッションは常に拒否する。
- Storageは非公開にし、ダウンロード時にサーバーで判定した短時間URLだけを発行する。

## 公開前に残る確認

- `lib/server/guidePhoneQueuedIssuance.ts` に非同期受付・実行の境界を追加した。受付はサーバーで生成したUUID・電話番号・受付時刻の永続キュー保存だけを待ち、ガイド照会やSMS送信はワーカーが行う。受付IDをチャレンジIDへ引き継ぐ。120秒以上滞留した要求は送信せず失効する。実キュー・公開ルートは未接続。キュー内の電話番号の保存期限と削除、非公開アクセス、アクセス元・全体の乱用制限を導入前に確定する。アダプターはワーカーを受付中に直接実行せず、登録有無で受付処理を分岐させない。
- `lib/server/guidePhoneIssuanceAdmission.ts` は、同一の信頼できるアクセス元を1分間に5件、システム全体を1分間に60件までに制限する純粋な判定を追加した。公開ルートは、ブラウザーJSONや生のIPではなく、エッジ側で導出した復元不能な識別子だけを渡す。実装時はアクセス元・全体の直近受付時刻を読み取り、許可の記録までを原子的に行う。拒否はキューへ入れず、認証要求と同じ一般受付応答にする。閾値・識別子の鍵管理・プロキシ構成はDODOの実インフラ決定後に見直す。
- `lib/server/guideDocumentAccess.ts` は、署名済みセッションから得たガイドIDで一覧を絞り、取得結果も所有者・`final`状態を再照合する。外部に返す一覧は書類ID・種別・対象月だけとし、Storageキーや口座情報は含めない。ダウンロードは同じ再照合の後、最大60秒の署名URLだけを返す。実DB/非公開Storage・公開APIは未接続。
- `lib/server/guideFinancialDocuments.ts` は、確定済み精算データから描画用の変更不能なスナップショットを作る。取込明細とCOM・DODO手数料・ガイド支払額の各合計を独立に照合し、未決定の計算式は推測しない。受取書は`paid`になった支払だけを対象とし、精算書のSHA-256と支払額が一致しなければ作成しない。訂正再発行では版番号と差替え元書類IDを必須にする。現段階はローカルのデータ生成・改ざん検出だけで、PDF描画・電子署名・DB保存は未接続。
- `lib/dodo/guideFinancialDocumentView.ts` は、検証済みスナップショットだけを日本語・円表示の印刷用表示モデルへ変換する。`/documents`には架空データのA4プレビューを追加した。受取書には対象精算書番号と支払日を明示するが、口座・電話番号・Storageキー・WeChat情報は扱わない。ブラウザー印刷のレイアウト確認であり、実PDF・受領意思・電子署名・実送付を示すものではない。
- 長い精算明細は同表示モデルで最大12行ずつに分割し、各ページへ見出し・ページ番号を再掲する。合計額は最終ページだけに表示し、行の欠落・並べ替えが起きないことをローカルテストで確認する。実ブラウザーと実プリンターでの余白・改ページ確認は未実施。
- `lib/server/guideReceiptAcknowledgement.ts` は、署名済みガイドセッションの本人が所有する`final`受取書について、`pending`から`acknowledged`への1回だけの確認を扱う。保存アダプターには旧状態との原子的compare-and-setを要求し、同時操作・再操作は成功扱いにしない。これはローカルの確認記録であり、電子署名や法的な受領意思としてはまだ扱わない。
- `lib/server/guideReceiptAcknowledgementAudit.ts` は、確認イベントUUID・書類ID・ガイドID・確認対象の受取書SHA-256・サーバー確認時刻だけを変更不能な監査レコードへ固定し、正規化したレコード全体のSHA-256で事後の改ざんを検出できるようにする。電話番号・Cookie・セッショントークン・IP・User-Agentは記録しない。将来のDB実装では確認状態のcompare-and-setと監査レコード作成を同じトランザクションで確定する必要がある。現段階はローカル生成だけで、電子署名や法的な同意を示すものではなく、実DBには未接続。
- `lib/server/guideReceiptAcknowledgementTransaction.ts` は、受取書の旧状態・新状態・監査レコード・監査SHA-256を1個の変更不能な保存単位にまとめる。保存アダプターには、旧状態の全項目compare-and-set、確認済み状態への更新、一意な監査イベント挿入を同一トランザクションで行い、競合時はどちらも保存せず`false`を返す契約を要求する。メモリーアダプターで再操作と同時操作を検証しているが、実DBトランザクション・実ルートにはまだ接続しない。
- 将来の受取書確認APIは `lib/server/guideReceiptAcknowledgementHttp.ts` の入力境界を通す。JSONは受取書UUID 1項目だけを許可し、余分な項目・不正UUIDを処理前に拒否する。存在しない・他人・未確定・取消済み・再確認・更新競合は同じ`unavailable`応答にまとめる。内部障害は固定の非公開イベントと固定503応答だけにし、セッション・書類ID・例外内容を漏らさない。実HTTPルートとDB保存はまだ接続しない。
- `lib/server/guideReceiptAcknowledgementService.ts` は上記HTTP境界と監査付き1回限りの確認処理を接続し、公開ルートから永続化方式を分離する。メモリー保存による結合テストで、正常確認、再操作、他人の書類、不正JSON、同時操作、保存障害を通し、同時操作ではcompare-and-setに成功した1件だけを確認済みとし、監査記録も同じ1件だけ作る。実ルート・実DB・実Cookieにはまだ接続しない。
- 将来の画面操作は `lib/server/guideReceiptAcknowledgementMutation.ts` のサーバー変換層を通す。ここでは `dodo_guide_session` だけを読み、スタッフ用Cookie・任意ヘッダー・別の署名鍵へフォールバックしない。厳格な入力検証と本人確認を通過した場合だけ監査付きトランザクションへ進む。Cookie取得失敗と保存障害は固定の非公開イベントと直列化可能な固定結果へ変換する。実`cookies()`、Server Action、DB、画面ボタン、キャッシュ再検証はまだ接続しない。
- `lib/dodo/guideReceiptAcknowledgementForm.ts` は将来の確認ボタン用に、待機・送信中・確認済み・利用不可・再試行可能の状態遷移を固定する。送信中は二重送信を開始せず、別の送信IDに属する古い応答は無視する。一時障害だけ再試行を許可し、存在しない・再確認済み・権限不足・不正要求は同じ再読み込み案内にまとめる。現在の画面にはまだ実ボタンを表示しない。
- `lib/dodo/guideReceiptAcknowledgementView.ts` は確認状態を「未確認・確認済み・取消済み」へ変換し、`/documents`の架空受取書へ表示する。確認済み時刻は日本時間で表示するが、現状の画面には確認ボタンや実API呼出しを置かず、状態表示のローカル確認だけを行う。
- ワーカーの再試行・同時実行に対して、保存先がチャレンジIDの一意性と電話番号ごとの発行制限を原子的に保証する必要がある。SMS失敗時も保存を取り消さず、同じ要求を再発行しない。キュー・保存先・送信先は現状テスト用の偽実装だけで検証している。
- 確認API境界では、存在しない・期限切れ・ロック・使用済みのチャレンジにも通常の照合と同じHMAC検証を1回実行する。結果にかかわらず拒否し、状態保存・セッション作成はしない。暗号処理を省略する時間差を減らす対策であり、DB照会・更新やネットワークを含めた一定時間応答を保証しない。
- 発行API境界の成功・拒否・障害で応答の形式・長さ・ステータス・ヘッダーを統一した。登録番号の推測を防ぎ切ったわけではなく、送信サービスやDBにかかる処理時間の差は未対策。公開前に非同期受付の設計、確認APIでの存在しないIDと実在IDの処理時間差、アクセス元の乱用制限を検証する。単純な固定待機だけで安全とは扱わない。
- `tests/guidePhoneFlow.test.mjs` は実際の発行・照合・署名関数を接続して、認証成功、再利用拒否、同時確認で1件だけ成功、5回失敗のロック、有効期限、再送制限を確認する。保存先とSMS送信先はテスト専用のメモリー実装であり、実DB・端末・ブラウザーでの検証ではない。

## WeChat通知

WeChatは「書類が準備できた」という通知に限定します。精算額、口座番号、PDF本体、認証コードはWeChatメッセージへ入れません。実接続前に、DODO用の公式アカウント・App ID・秘密鍵の管理責任者・同意文言・通知テンプレートを確定します。

## 実装開始に必要なもの

1. DODO専用の認証コード送信サービス（SMSまたは音声）の契約・送信元・費用上限
2. DODO用WeChat公式アカウントと、通知だけに必要な権限
3. DODO専用Supabaseであること、バックアップ、テスト用ガイド1名
4. 精算書・受領証の確定条件、訂正・再発行の運用ルール

これらの確認後にだけ、認証コード送信、DB migration、Storage、実通知を有効化します。
